# シナリオ作成ルール v1

## 1. このメモの目的

このメモは、シナリオ資料を人間とCodexの双方が迷わず読み取り、後からゲームデータへ変換できるようにするための共通ルールを定める。

シナリオを作る段階では物語の内容を優先する。ただし、設定資料、シナリオ本文、ゲーム実装用JSONの役割は分け、同じ情報を複数の場所で正本として管理しない。

---

## 2. 保存場所

シナリオ関係のMarkdownは、原則として次の場所に保存する。

```text
docs/world/scenario/
├─ 00_シナリオ作成ルール_v1.md
├─ 01_シナリオ全体概要_v1.md
├─ 02_時系列・章構成_v1.md
├─ chapters/
│  ├─ chapter_01/
│  │  ├─ 00_章概要.md
│  │  └─ scene_01_シーン名.md
│  └─ chapter_02/
├─ characters/
├─ events/
└─ drafts/
```

- `01_シナリオ全体概要_v1.md`: 物語の開始状況、目的、主要な対立、結末候補
- `02_時系列・章構成_v1.md`: 世界上の出来事と章・シーンの順序
- `chapters/`: 実際にプレイヤーが体験する本編
- `characters/`: シナリオ上の人物の目的、関係、登場時期
- `events/`: 複数の章やエリアから参照するイベント定義
- `drafts/`: 未整理の案。確定情報の参照先にはしない

ファイルが増えるまでは、空フォルダを先に作る必要はない。必要になった分類から追加する。

---

## 3. 情報ごとの正本

同じ内容が食い違わないように、情報の種類ごとに正本を一つだけ決める。

| 情報 | 正本 | シナリオ側での扱い |
|---|---|---|
| 世界の法則、歴史、種族、技術 | `docs/world/` 内の該当設定メモ | 要約せずファイル名と見出しを参照する |
| 施設の役割、内部構造 | `docs/world/11_AA施設詳細メモ_v1.md` | 使用する施設ID・名称だけを書く |
| 施設の位置、道路、接続経路 | `docs/world/10_AAマップ経路・施設配置メモ_v1.md` | 移動元・移動先・経由地点を書く |
| シナリオの因果関係、登場順、会話 | `docs/world/scenario/` | ここを正本とする |
| ゲーム内で再生する会話イベント | `src/data/exploration/dialogueEvents.json` | シナリオの会話を実装用IDと再生順へ変換したデータ |
| エリアID、出口、BGM、マップ参照 | AreaMasterなどのゲームデータ | シナリオでは要求だけを書き、数値を重複管理しない |
| 開いた扉、倒した敵、回収済み宝箱 | AreaState・セーブデータ | 変更させる状態IDだけ指定する |
| 物語全体の進行状態 | EventFlag | シナリオ側で必要なフラグIDと変更条件を定義する |

設定資料とシナリオが矛盾した場合、Codexは独断で統合しない。矛盾箇所、参照元、考えられる修正案を示し、どちらを変更するか確認する。

## 4. ファイル名とID

### 4.1 ファイル名

- 日本語の表示名は、内容が分かる範囲でファイル名に使用してよい
- 並び順が重要な資料には、先頭に2桁の番号を付ける
- 大幅な方針変更時は `_v2` のように版を上げる
- 日々の小さな修正ではファイルを複製せず、同じ版を更新する
- `最終版`、`最新版`、`新しい方`のような判別しにくい名前を使わない

### 4.2 ゲーム連携用ID

ゲームから参照する可能性があるものには、一意のIDを付ける。

```yaml
scenarioId: main_ch01
sceneId: main_ch01_scene_01
eventId: evt_middle_rescue_01
areaId: middle_residential_01
characterIds:
  - player_main
  - npc_resident_01
requiredFlags:
  - story_prologue_complete
setFlags:
  - middle_rescue_started
```

- IDは半角英小文字、数字、アンダースコアを基本とする
- 表示名を変更してもIDは変更しない
- 同じ対象に別のIDを作らない
- 仮IDには `tmp_` を付け、確定前であることを明示する
- IDを変更するときは、参照しているシナリオとゲームデータを同時に確認する

## 5. 確定度の書き方

各資料の冒頭に、内容の確定度を記載する。

```yaml
status: draft
```

使用する値は次の4種類とする。

```yaml
idea: 断片的な案。別案と競合してよい
draft: 仮シナリオ。実装の基準にはしない
review: 流れは固まり、矛盾確認中
confirmed: 現在の正本。実装の基準にしてよい
```

Codexは `idea` または `draft` の内容を、明示なしに確定設定として別資料へ広げない。

---

## 6. 章とシーンの分け方

- 章は、プレイヤーの大きな目的が一つ完了する単位とする
- シーンは、場所、時間、操作目的のいずれかが大きく変わるところで分ける
- エリアを移動しただけでは、必ずしも別シーンにしない
- 一つのシーンが長くなった場合は、会話、探索、戦闘、イベント後処理に区切る
- 一本道ではない場合、分岐条件と合流地点を明記する

シーン本文では、演出の文章と実装条件を分ける。

```markdown
## 演出・内容

居住広場に入ると警報灯だけが点灯している。
住民は整備工房側へ避難している。

## ゲーム上の条件

- 開始エリア: `middle_residential_01`
- 発生条件: `story_prologue_complete == true`
- 登場NPC: `npc_resident_01`
- 完了条件: 整備工房入口でNPCと会話する
- 完了時に立てるフラグ: `middle_rescue_started`
```

---

## 7. シーンファイルの必須項目

各シーンは、原則として次の形式で記載する。

````markdown
# シーン表示名

```yaml
scenarioId: main_ch01
sceneId: main_ch01_scene_01
status: draft
areaIds:
  - middle_residential_01
characterIds:
  - player_main
requiredFlags: []
setFlags: []
previousSceneId: null
nextSceneIds:
  - main_ch01_scene_02
```

## 目的

このシーンでプレイヤーが理解し、達成することを書く。

## 開始状態

開始位置、同行者、周囲の状態を書く。

## 進行

プレイヤーの行動順に、探索、会話、戦闘、分岐を書く。

## 会話

話者IDと台詞を書く。仮台詞には `仮` と記載する。

## 分岐と条件

選択肢、必要フラグ、分岐先、合流先を書く。

## 終了状態

変更されるEventFlag、AreaState、所持品、NPC状態を書く。

## 実装メモ

必要な入口、出口、イベント地点、演出、画像、音声を書く。

## 未決事項

決まっていない内容だけを箇条書きにする。
````

`目的`、`開始状態`、`進行`、`終了状態`は省略しない。未定の場合は空欄にせず `未定` と書く。

---

## 8. 会話の書き方

会話は、表示名ではなく話者IDを併記する。

```text
[npc_resident_01 / 居住区の住民]
「中央環状路へは行かない方がいい。」

[player_main / 主人公]
「何があった？」
```

表情や動作が必要な場合は台詞と分ける。

```text
演出: npc_resident_01 が環状路側を振り返る。
表情: fear
```

- キャラクター名の表記揺れを作らない
- 感情、表情、立ち位置、吹き出しの向きは必要な場合だけ記載する
- 話者不明の音声は `system`、`narration`、`unknown_voice`など役割が分かるIDを使う
- 台詞の改稿だけでイベント条件を変更しない

---

## 9. 分岐と状態変更

分岐は文章だけで済ませず、条件と結果を対で書く。

```yaml
branches:
  - condition: rescue_event_complete == true
    result: 救助済みNPCが広場に現れる
    nextSceneId: main_ch02_scene_03a
  - condition: rescue_event_complete == false
    result: 広場は無人のまま
    nextSceneId: main_ch02_scene_03b
```

- 物語全体に影響する結果はEventFlagへ保存する
- 特定エリア内だけの変化はAreaStateへ保存する
- 扉や出口の利用条件と、物理的な通行止めは区別する
- 条件未達の出口は、特別な指定がない限り「エリア移動できない」だけとし、通路上の当たり判定にはしない
- 一度だけ発生するイベントは、再発防止用の完了フラグを持たせる

---

## 10. シナリオから実装へ渡す情報

シナリオ段階では、ゲームデータそのものを丸ごと書かない。実装に必要な要求を `実装メモ` にまとめる。

```yaml
implementationRequirements:
  areaIds:
    - middle_residential_01
  spawnId: entrance_main
  eventPoints:
    - event_resident_warning
  requiredCharacters:
    - npc_resident_01
  requiredImages:
    - 居住区の警報灯
  requiredAudio:
    - alarm_low
  stateChanges:
    eventFlags:
      middle_rescue_started: true
    areaState:
      alarmState: active
```

実装開始時にCodexがこの項目を読み、既存のAreaMaster、AreaScene、AreaConnection、AreaState、EventFlag、キャラクターライブラリとの対応を確認する。

ゲーム内で順番に表示する会話は、ゲスト画面の「会話イベント作成」で編集し、`src/data/exploration/dialogueEvents.json`へ保存する。シナリオ本文の台詞が正本であり、このJSONは会話ウィンドウで再生するための実装データとして扱う。

## 11. Codexが読む順番

シナリオに関する作業を行うとき、Codexは原則として次の順番で確認する。

1. この作成ルール
2. `01_シナリオ全体概要_v1.md`
3. `02_時系列・章構成_v1.md`
4. 作業対象の章概要
5. 作業対象のシーン
6. シーンから参照されている世界観・施設・経路メモ
7. 関係するゲームデータと現在の実装

存在しないファイルは読み飛ばす。資料がまだないことと、設定上存在しないことは区別する。

---

## 12. Codexが編集するときのルール

- 明記されていない設定を確定事項として補完しない
- 補完が必要な場合は `提案` または `仮案` と明示する
- `confirmed` の内容を変更する場合は、変更理由と影響する参照先を示す
- 矛盾を発見しても、片方を無断で削除しない
- 既存のID、固有名詞、時系列を変更する前に参照箇所を検索する
- シナリオ変更とゲーム実装変更を同時に行った場合は、両方の差分を確認する
- 未決事項を推測で埋めず、資料の `未決事項` に残す
- 新しいシナリオファイルを追加した場合は、全体概要または章概要から参照できるようにする
